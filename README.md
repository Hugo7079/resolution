# 解析度 · Resolution

> 每天提高你看設計的解析度

每天介紹一件設計，加上當天的作品流與產業動態。
不是設計新聞聚合 —— 新聞只是配菜，**主菜是「看設計的方法」**。

讀者有兩種，必須同時餵飽：
  ‣ **不懂設計、但想認識的人** —— 他要的是「原來可以這樣看東西」
  ‣ **圈內人** —— 他要的是「這個觀察我沒想到」

這個站是一個**踏入設計的媒介**，不是給同行看的評論版。
所以每篇的每個角度都必須附一句白話翻譯（「所以呢」），
入口與出口一個術語都不准出現。

讀者累積的不是資訊量，是判準。

---

## 一、每日節奏

**七天都是同一件事：介紹一件設計。**

原本的「週五跨界／週六設計史／週日休息」拿掉了。理由：那兩天談的是議題和脈絡，
不是一件看得到的作品，讀者每天打開的期待會不一樣，
而「每天一件設計」這個承諾一旦有例外就不成立。

跨界與歷史沒有消失，它們降級成「多角度欣賞」裡的兩個鏡頭
（`context`／`time`），在作品本身帶得動的時候才談 —— 那反而比硬排一天更自然。

分類用**絕對日數輪播**（`date.toordinal() % 4`），不綁星期：
四個分類配七天除不盡，綁星期會讓某一類永遠比別類多曝光。

### 選題不綁當天的新聞

每天抓到的東西先進**作品池**（`output/pool.json`）存著，不是當天用不到就丟。
今天的主角從整個池子挑，用過的標記起來不再出現。

  ‣ 保鮮期 **90 天** —— 不必是今天最新的，但不能是幾年前的老東西
  ‣ 池子越跑越厚，選題品質單調上升
  ‣ 抓取掛掉還有貨，順便解掉「RSS 掛了就整天失敗」

舊的做法只看當天抓到的前幾則、而且主要按摘要長度排序，
所以長篇評論永遠贏過作品介紹（實測挑到一篇談某邦選前活動的新聞稿）。
現在的評分問的是「這是不是一件看得到的作品」：
作品源 → 分類對得上 → 標題不像新聞 → 有內文但不是長篇評論。

## 二、分類（四類）

分類是**篩選器**不是目錄。原則：互斥、一眼可判、每天都有貨。

| id | 分類 | 讀者是誰 |
|---|---|---|
| `visual_brand` | 視覺與品牌 | 平面／品牌／包裝設計師（人口最大宗） |
| `interface_ux` | 介面與體驗 | 產品設計師、前端、PM |
| `product_object` | 產品與物件 | 工設、選品、製造端 |
| `space_env` | 空間與環境 | 建築、室內、策展 |

**動態影像併入「視覺與品牌」**，不獨立成類 —— motion graphics 本質是動起來的平面，
且獨立後供給撐不住（來源只有 Motionographer 一家穩定出貨）。

### 邊界判準（寫死在 prompt，避免每天分得不一樣）

- 最常搖擺的是「展場指標系統算空間還是視覺」→ **以使用者是否身處其中為準**：
  身處其中歸 `space_env`，拿在手上或看螢幕歸 `visual_brand` / `interface_ux`。
- 實體產品上的圖形（包裝、標籤）→ `visual_brand`；產品本身的形態材質 → `product_object`。
- 網站／App 的視覺風格 → `interface_ux`（不拆成兩類，以載體為準）。

## 三、版面結構

```
┌─────────────────────────────────────┐
│  今日拆解  （1 件，佔版面 70%）      │  ← 主菜，不受篩選影響
│  大圖 + 七軸分析                     │
├─────────────────────────────────────┤
│  作品流   （6–8 件卡片牆）           │  ← 圖 + 一句話 + 出處，不做 LLM 分析
│  純視覺，滑五秒的滿足感               │
├─────────────────────────────────────┤
│  產業動態 （3–4 則列表）             │  ← 真新聞：收購、獎項、AI 衝擊、訴訟
└─────────────────────────────────────┘
```

### 前端規則

1. **預設全看**，不逼使用者一進來先選分類。
2. 四個 chip 橫排（不用下拉選單，一眼看完），可複選，狀態存 localStorage。
3. **篩選只作用在作品流與產業動態**。今日拆解永遠顯示 ——
   每天只有一件，被篩掉主版位就空了。分類均衡靠輪播保證，不靠篩選。
4. 產業動態不套四分類（收購、訴訟本來就跨領域），保持無分類列表。
   多一套分類邏輯只會讓使用者多想一次。

## 四、文章結構：三層漏斗

七個並列的軸是寫給同行看的評論，圈外人不知道從哪進去。改成有順序的三層：

### 一、先看見（零術語）

  ‣ **hook** — 一句話：這件東西在做什麼、為什麼值得停下來看三秒
  ‣ **what_it_is** — 品類、誰做的、給誰用的、什麼時候的事

非設計的人只讀這一句就走也算數，所以它不能長得像前言（版面上字級比內文大）。

### 二、多角度欣賞（3–5 個，不固定）

鏡頭池：顏色／字／東西怎麼擺／用什麼做的／它在說什麼／放在同類裡看／
它放棄了什麼／用起來會怎樣／放到時間裡。

**挑這件作品真的談得動的，不要硬套。**
對一張海報硬談「用什麼做的」、對一張椅子硬談「三秒讀到什麼」，出來的都是廢話。

每個角度強制配一句 **「所以呢」** —— 把觀察翻譯成讀者自己生活裡的經驗。
這句是這個站的樞紐：少了它，這就只是一篇專業評論。

### 三、帶走（兩份）

  ‣ **給每一個人** — 下次在生活裡看到什麼，可以用今天這雙眼睛看。
    **不必是設計師才做得到**（非設計的人沒有案子、沒有客戶）
  ‣ **給做設計的人** — 一個明天就能用的具體手法

版面上圈外人那份用實心底、圈內人那份收斂成描邊 —— 視覺上先給不懂的人，這是立場。

### 三條寫作紅線

**紅線一：禁止抽象形容詞。**
「配色和諧、層次分明、留白得宜」這種句子寫一百篇都一樣，讀者第三天就走。
強制引用可觀察的具體物：字體名稱、色票 hex、格線欄數、實際尺寸、材質工法。

**紅線二：批評寫成取捨，不寫成評分。**
不是「這裡做得不好」，而是「為了得到 A 犧牲了 B；如果目標換成 C，這個選擇就不成立」。
理由：台灣設計圈很小，評分表會出事；而且取捨分析的教育價值本來就更高。

**紅線三：術語要翻譯。**
術語不是不能用，是不能不解釋。
`hook` 和「給每一個人」一個術語都不准出現；
角度裡可以用，但每個用到的詞都要進 `glossary`，用一句話講給完全不懂的人聽。

### 品質閘（可驗證，不靠祈禱）

| 檢查 | 門檻 |
|---|---|
| 具體物 `concretes` | ≥ 4 項，而且要能在原文或讀圖描述裡溯源 |
| 角度數 | 3–5 個，每個都要有 `body` 和 `so_what` |
| 具體物引用 | 至少一個角度引用到 ≥ 2 項具體物 |
| 入口與出口 | 零術語；「給每一個人」不准預設讀者是設計師 |
| 術語 | 用到的都要在 `glossary`（缺的自動補寫，不整篇打回） |
| 簡體字 | 轉換後不得殘留 |
| 禁用詞 | 抽象形容詞、評分式批評 |

沒過就重寫一次，再沒過**換下一個候選**（一天最多試 3 個）。
三個都不過才不出這篇 —— 寧可失敗也不出空話。

### 簡繁轉換的坑（實測）

不能把整段丟給 opencc。`s2twp` / `s2tw` / `s2t` **三個設定都會**把已經正確的繁體字改壞：

```
「不是只顧著好看」→「不是隻顧著好看」   （只 被當成 隻 的簡體）
「連接機制」      →「連線機制」         （s2twp 的詞彙表，用在傢俱上是錯的）
```

模型吐出來的東西九成是繁體、偶爾夾一兩個簡體字，整段轉換的期望值是負的。
改成**逐字轉換 + 歧義字保護**（`只后里表干云面系制松谷丑几卜斗冲板` 一律不動），
詞彙層另外用明列的對照表（界面→介面、软件→軟體）。

代價：來源真的是簡體時，這些歧義字不會被轉。
這個方向的錯誤小得多 —— 少轉一個字只是不夠道地，轉錯一個字是別的意思。

## 五之二、語言平衡機制

**這是本專案的核心難題。** 英語圈來源量是其他所有語區加起來的三倍以上，
放任演算法自然排序，站上會 90% 英文 —— 那就失去做這個站的意義。

### 硬性語言配額（寫進 pipeline，不是建議值）

| 區塊 | 配額 |
|---|---|
| 作品流 6–8 件 | **至少 2 件來自非英語圈**（日／韓／歐陸／華語） |
| 產業動態 3–4 則 | **至少 1 則來自華語圈**（含 Google News 中文補件） |
| 深度拆解 | 地區輪替軟約束：每月至少各 1 次拆解日本、歐陸、華語圈的作品 |

配額不足時**寧可少放一件**，不要用英文源補滿 —— 版面短一格沒人會發現，
但連續兩週全英文，讀者會發現。

### 台灣內容的破口，誠實面對

繁中真正的設計來源只剩 Shopping Design 一家（9 筆）。三條補救路線：

1. **Google News 中文 query**（既有能力，直接沿用）
2. **官網公告頁 HTML 抓取**：台灣設計研究院、金點設計獎、松菸、華山
   —— 無 RSS 但更新低頻，一週跑一次即可，價值高
3. **接受現實**：台灣設計「新聞」產量本來就低。與其硬湊，
   不如把台灣內容集中在「產業動態」區，作品流以國際為主

不推薦自架 RSSHub 轉 IG／FB 專頁 —— 灰色地帶，且維護成本會吃掉整個專案。

### 輸出語言

不論來源是英／日／韓／德／法／西／簡中，**輸出一律繁體中文**。
既有 pipeline 已在做英→中，多語輸入對 Mistral 不構成問題。
簡中來源要特別做**簡轉繁 + 用詞在地化**（「界面」→「介面」、「軟件」→「軟體」）。

## 六、圖片策略與版權

### 取圖順序

1. `<enclosure>` type=image
2. `media:content` / `media:thumbnail`
3. 內文 `content:encoded` 的第一張 `<img>`
4. fallback：抓文章頁 og:image

**完全不使用 AI 生成圖。** 對設計媒體來說，生成的封面是自傷。

影片：feed 裡幾乎拿不到，需從文章頁挖 YouTube / Vimeo embed。列為加分項，不列主力。

### 版權原則（四條，不可妥協）

1. **只存縮圖**（長邊 ≤ 600px）自用，原圖一律連回來源
2. 每張圖**強制帶設計師／工作室署名 + 原文連結**，沒有出處就不出這張
3. 站上留**下架聯絡管道**
4. **絕不用生圖模型「重繪」他人作品** —— 那是完全不同層級的問題

評論用途下展示作品站得住，但 rehost 全尺寸原圖的風險高一截，不值得為此省那點流量。

## 七、技術路線

沿用「晨誌 Morning Ledger」的骨架，約 60% 可直接搬：
`doc_model` / `local_store` / `firestore_writer` / `web/` / cron / 部署全部原封不動。

要重寫的三塊：

| 模組 | 改動 |
|---|---|
| 來源層 | 全換；`fetcher` 增加圖片欄位抽取與語區標記 |
| 分類 | 5 類 AI 分類 → 4 類設計分類 + 邊界判準 |
| **產文引擎** | 全新。兩段式 vision + 三層漏斗 prompt + 三條紅線 |

### 產文引擎採兩段式（重要）

不要讓 Cloudflare 的模型直接寫文章 —— 它的繁中生成會簡繁混雜、用詞生硬，
而這篇文章是整個產品的門面。分工如下：

```
第一段：Cloudflare Workers AI  @cf/meta/llama-3.2-11b-vision-instruct
        輸入：作品圖 1–4 張
        輸出：英文的「客觀視覺描述」—— 字體特徵、色票、構圖格線、材質工法
        （只描述看到什麼，不評論）

第二段：Mistral  ministral-14b-latest
        輸入：視覺描述 + 原文 + 三層漏斗框架 + 三條紅線
        輸出：繁體中文的「今日一件」
```

### 文字模型：為什麼是 ministral-14b（2026-09-07 實測）

金鑰的額度是**分模型**發的，不是整個 workspace 一個數字：

| 模型 | 狀態 |
|---|---|
| `ministral-3b / 8b / 14b`、`open-mistral-nemo`、`codestral` | ✓ 30 req/min、937k tokens/min |
| `mistral-small / medium`、`magistral` | ✗ `x-ratelimit-limit-req-minute: 0` |

能用的裡面挑最大的一顆，而且正好是開源小模型那一系。同題實測：

  ‣ **14b** — 白話翻譯寫得最準，「所以呢」有真的翻譯到讀者身上
  ‣ **8b** — 三個角度用同一個句型（「這代表設計可以用 X，讓你…而不需要說…」）
  ‣ **nemo** — 幻覺明顯，憑空生出「左上角男性臉孔比例較大」這種畫面裡沒有的東西

`src/config.py` 的 `LLM_PROVIDERS` 把 base_url／model／rpm 綁成一組
（Mistral 的 base_url 帶 `/v1`、其他家不一定帶，只換 key 必壞）。
之後要換自架的開源模型，把 `RES_LLM_PROVIDER` 指到 `ollama` 那組就好，程式不用動。

好處有三：避開 CF 模型的中文弱點；CF 只吐短英文描述，
**output token 的 neuron 單價是 input 的 14 倍**，讓它少講話等於成本直接掉一個量級；
兩段可獨立除錯。

### Cloudflare 免費額度試算（與晨誌共用同一個帳號）

免費額度是 **10,000 neurons／天／帳號**，兩個專案共吃同一鍋。

| 項目 | 計算 | neurons／天 |
|---|---|---|
| 晨誌 生圖（現況 68 張） | 68 × 57.6 | **3,917** |
| 晨誌 生圖（上限 150 張） | 150 × 57.6 | 8,640 |
| 解析度 讀圖（4 張＋重試） | 約 4 × 34 + 重試 | **約 170** |

llama-3.2-11b-vision 的單價是 4,410 neurons／M input token、61,493／M output token。
單次讀圖以 input 3,500 tokens、output 300 tokens 估算 ≈ 34 neurons。

**結論：額度非常充裕。** 依現況用量，剩餘 6,083 neurons 可以跑 35 次拆解，
而每天只需要 1 次（約 170）。用量只佔剩餘額度的 3%。

**但有一個時序風險必須處理**：晨誌是貪吃的那個，若某天新聞暴量、生圖跑到上限 150 張，
會吃掉 8,640，剩下 1,360 —— 仍然夠，但若晨誌先跑完才輪到解析度，餘裕就很薄。

處理方式（二選一）：
- **排程錯開**：解析度 05:30 先跑（用量小、跑得快），晨誌 06:00 後跑
- **硬留額度**：晨誌把生圖上限從 150 降到 120，永遠替解析度留 1,700 neurons
  （既有 repo 已有保留額度的機制，commit `b79779d`）

建議兩個都做，成本是零。

### 週六「設計史」的受眾與寫法

鎖定兩種人，寫作必須同時餵飽：

1. **不太懂設計、但想了解的人** —— 靠「今天的事」進來
2. **本來就在圈內、喜歡回味的人** —— 靠「新角度」留下

這決定了寫法：**用本週事件當入口 → 帶出歷史脈絡 → 給老手一個沒想過的連結**。

- 術語第一次出現時用一句話帶過，但**不要整篇科普腔** —— 那會趕走第二種人
- 不要寫成維基百科條目。歷史是用來解釋「為什麼今天會這樣」的
- 不預先建素材庫，代表每週都得從本週實際抓到的東西裡現找連結。
  找不到夠強的就退回「本週最有話題的一件 × 它的血緣」，不硬掰
